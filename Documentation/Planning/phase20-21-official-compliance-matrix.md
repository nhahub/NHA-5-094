# Phase 20–21 Official Compliance Matrix

**Audit date:** 2026-10-11  
**Status source of truth:** this matrix and [the A–K compliance audit](phase20-21-official-compliance-audit.md).

## Scope and authority

The official acceptance inventory is taken from:

1. `Documentation/04-operations-and-roadmap.md` §33 for the Phase 20 and Phase 21 roadmap definitions.
2. `Documentation/Verifia_Detailed_Implementation_Checklist.md` §§20–21, plus §2.12 for the documented event names and fields.
3. `Documentation/02-architecture.md` and `Documentation/03-database-schema.md` as supporting definitions for event meaning and the transactional outbox.

Requirement classifications follow the audit request: **A** is an explicit requirement in original project documentation/roadmap; **B** is an explicit item in the actual implementation checklist; **C** is a previously generated proposal; **D** is a technical task derived because it is necessary to satisfy an A/B requirement. The rows are individually classified in the matrix. All Phase 20/21 checklist entries were present in the inspected source; their checkbox status at audit start is recorded per row. The pre-Phase-21 Git baseline had Phase 21 boxes unchecked; the working checklist at audit start had those Phase 21 boxes checked from prior work.

`phase20-production-security-implementation-plan.md` and `phase21-durable-events-implementation-plan.md` are later planning documents. Their “recommended policy decisions,” proposed workstreams, and additional recommendations are not independent official acceptance criteria unless they also appear in the original roadmap/checklist or have a recorded scope approval. The related C proposals are listed separately below so they are not confused with official requirements.

Checklist statuses follow the requested terms: **VERIFIED COMPLETE**, **IMPLEMENTED, NOT FULLY VERIFIED**, **PARTIALLY COMPLETE**, **MISSING**, **INCORRECT**, and **BLOCKED**. Phase 20 items were unchecked in the checklist at audit start. Phase 21 items were checked in the working checklist; this audit re-tested them and records live-service limitations below.

## Original-source and checklist discrepancies

- The roadmap's Phase 20 production-default/CORS/docs/upload/external-model policy scope maps to checklist §20 Data and External Models; no roadmap security requirement in §33 was found missing from the checklist.
- The roadmap's Phase 21 durable-delivery, retries/replay/idempotency/duplicate handling across multiple workers, and dependency-aware readiness requirements are represented by checklist §21's durable-delivery and liveness/readiness items. The journey items and actor/timestamp/tool-link details also appear directly in checklist §21.
- Database schema §26.41 adds an atomic event-plus-outbox transaction contract not stated verbatim in checklist §21. This is classified **D** as technically necessary to satisfy durable delivery, and was implemented/tested in this audit.
- Every official Phase 20/21 item in the inventory has an identifiable source. No checklist item in §§20–21 was found to be only an unapproved AI proposal; later plan-only work is separated in the table above.

## Overall disposition

- **Phase 20: PARTIAL.** Local security and data-boundary controls pass. Provider retention/training and route/data-class approval remain open; no malware scanner is installed; production storage/network topology was not verified in this audit.
- **Phase 21: PARTIAL.** The documented event sequence, atomic writes, durable delivery behavior, authorized history, and API readiness are covered by automated tests. Current Docker-backed multi-worker/readiness rechecks are outstanding; prior live probes are historical. No real ERPNext, external-provider business-data, or exactly-once external-effect claim is made.
- **Phase 17: BLOCKED.** Restore its original locally agreed threshold file to run that acceptance gate; this is not a Phase 20/21 failure.
