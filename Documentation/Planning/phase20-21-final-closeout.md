## 7. Durable-event and live Compose verification

Before running probes, `docker compose ps` showed the backend, frontend, PostgreSQL, Redis, and two event-worker containers Up; API, frontend, PostgreSQL, and Redis were healthy. The probes ran sequentially in the existing backend container:

```powershell
docker compose exec -T backend python scripts/phase21_worker_e2e.py --timeout 30
docker compose exec -T backend python scripts/phase21_worker_e2e.py --timeout 30 --simulate-expired-lease
```

Observed results: fresh trusted event **attempt 1**, one orchestration result; simulated expired `PROCESSING` lease **attempt 2**, one orchestration result. The script's `finally` block deletes only its generated organization; PostgreSQL foreign-key cascades remove that organization's event, outbox delivery, and result. No worker container was stopped or restarted.

The code uses a transaction-aware outbox write, PostgreSQL row claims with `FOR UPDATE SKIP LOCKED`, expiring leases, lease-token fencing, bounded retry/backoff, five-attempt dead-lettering, trusted-event replay, and persisted orchestration-result checks. Delivery deduplication protects the persisted dispatch result. It cannot make an external side effect atomic with PostgreSQL.

## 8. Production TLS, topology, storage, and provider review

These are release gates and remain **BLOCKED** until evidence comes from the actual target environment:

1. **TLS and edge:** provision the host reverse proxy and certificate, verify renewal, HTTPS redirects, forwarded headers and HSTS, and test browser/API traffic over the public hostname. Local HTTP at `127.0.0.1` is not TLS evidence.
2. **Topology and dependencies:** verify only the web edge is externally reachable; backend, PostgreSQL, and Redis stay private. Confirm PostgreSQL and Redis TLS/authentication, firewall/network allowlists, health monitoring, backup and restore, and database/cache reachability from the production Compose network.
3. **Secrets:** populate `.env.production` from approved secret storage; verify unique production secrets and rotation procedure without printing values. The checked-in template contains placeholders and is not a deployment secret source.
4. **Storage:** complete the production image build, then verify `id` returns `10001:10001` and `/app/data/storage` is `10001:10001` mode `750` with both fresh and existing named volumes. The existing local image inspected on 2026-10-11 predates the Dockerfile change and reports a blank `Config.User`; it is not evidence of the new runtime identity. Stop writers and take a verified backup before any permission repair. Verify authorized downloads, safe content disposition/type, and backup/cleanup access.
5. **Untrusted uploads:** uploads remain disabled by default in production because no scanner/quarantine integration exists. Before enabling them, deploy a maintained scanning flow or record a restricted-use risk decision and its owner.
6. **Providers:** complete the checklist in `external-model-provider-review.md` for each provider/model/endpoint: terms, retention/training, region, subprocessors, data categories, redaction, logging, legal/business approval, and incident handling. Keep production route policy at deny until route-specific approval is documented. No provider approval is claimed.
